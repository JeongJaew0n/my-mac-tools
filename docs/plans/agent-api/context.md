# context — agent-api

## 원 요청 (2026-09-21)

> 다 끝나면 이제 여기의 기능을 claude code나 다른 에이전트가가 사용할 수 있는 api 만들어줘.
>
> 이어서 할 작업은 api만들기야. 니가 알아서 설계하고 문서작성하고 그거대로 구현해. 물어보지마.

설계·문서·구현을 묻지 않고 진행하라는 지시다. 그래서 갈리는 결정을 `spec.md` 에
근거와 함께 적어 두었다 — 나중에 뒤집을 때 무엇을 보고 정했는지 남기기 위해서다.

## 기각 — 로컬 HTTP 서버

에이전트에게 가장 익숙한 모양이고 `curl` 예시를 쓰기도 쉽다. 두 가지가 걸렸다.

1. **이 앱에는 듣고 있는 포트를 보여주는 Tool 이 있다.** HTTP 서버를 열면 자기 목록에
   자기가 나타난다. 기능이 자기 자신을 관측 대상으로 만드는 것은 피하고 싶었다.
2. 포트는 같은 맥의 다른 프로그램에도 열려 있어 **토큰이 필요해진다.** 토큰을 도입하면
   "그 토큰을 어디에 두는가" 가 새 문제가 된다. 유닉스 소켓은 파일 권한이 그 일을 한다.

편의의 차이도 크지 않다 — `nc -U` 한 줄이면 부른다.

처음에는 `curl --unix-socket` 으로도 된다고 적었는데, 그것은 **유닉스 소켓 위의 HTTP** 를
위한 옵션이다. 이 서버는 HTTP 를 말하지 않으므로 `curl` 은 빈 응답을 준다 (실측).

## 기각 — MCP 서버

Claude Code 에는 가장 잘 맞는다. 다만 별도 프로세스와 stdio 브리지가 필요하고, 그것을
띄우고 죽이는 수명 관리가 또 생긴다. 셸 호출만으로 되는 API 를 먼저 만들고, MCP 로
감싸는 것은 `docs/api.md` 의 예시로 남긴다. 감쌀 대상이 있어야 감쌀 수 있다.

## 기각 — URL 스킴 (`mymactools://`)

앱을 깨우는 데는 되지만 **응답을 돌려줄 수 없다.** 상태를 읽는 것이 이 API 의 절반인데
그것을 못 한다.

## 기각 — CLI 서브커맨드를 앱 바이너리에 얹기

`MyMacTools ports list` 가 제일 짧다. 그런데 이 바이너리는 GUI 앱이라 그냥 실행하면
**두 번째 인스턴스가 뜬다.** 인자를 보고 갈라 돌게 만들 수는 있지만, 그 안에서 결국
돌고 있는 인스턴스와 통신해야 한다 — 소켓이 필요하다. 순서가 뒤바뀐 설계다.

## 쓰기를 허용한 이유

읽기만 주는 쪽이 안전하다. 그런데 이 API 의 쓸모는 "상태를 보고 조치" 에 있다 —
포트를 잡고 있는 프로세스를 찾아 끄고, 긴 빌드 전에 잠자기 방지를 켜는 것 같은 일이다.
읽기만 주면 절반이 사라진다.

대신 **물어볼 사람이 필요한 일은 거부한다.** 시스템 구성요소 중지는 앱에서 확인창을
띄우는데, API 호출자에게는 띄울 화면이 없다. 확인을 받을 수 없으면 하지 않는다.
덮개 Tool 도 같은 이유다 — 관리자 암호창이 에이전트 호출로 튀어나오면 사용자가
무엇 때문에 뜬 창인지 알 수 없다.

## 소켓 자리

`~/Library/Application Support/MyMacTools/api.sock`

샌드박스가 아니라 이 경로를 그대로 쓴다. 나중에 샌드박스를 켜면 컨테이너 안으로
옮겨야 하고, 그러면 컨테이너 밖의 에이전트가 못 닿는다 — 샌드박스를 검토할 때
이 API 가 먼저 걸린다는 것을 적어둔다.

유닉스 소켓은 **연결 전에 지워야** 한다. 앱이 강제 종료되면 파일이 남는데, 그 위에
다시 `bind` 하면 `EADDRINUSE` 다. 시작할 때 지우고 만든다.
