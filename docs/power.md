# 전력 소비 — 측정과 줄일 여지

2026-09-23, macOS 26.3.1 / Apple M3 Pro / 배터리 전원에서 실측한 것이다.
추정한 값은 그렇다고 표시했다.

## 요약

| 상태 | CPU | 환산 전력 |
|---|---|---|
| **창 닫힘** (메뉴바만) | **0.000%** | 측정 불가 (0 에 수렴) |
| **창 열림** (폴링 중) | **0.517%** | **약 38 mW** (상한) |

비교 대상 — 같은 방법으로 잰 다른 메뉴바 앱.

```
MyMacTools (창 닫힘)   0.000%
Dock                   0.000%
Raycast                0.033%
MyMacTools (창 열림)   0.517%
```

**창을 닫으면 완전히 잠잠하다.** 소비는 전부 창이 열려 있는 동안의 폴링에서 나온다.
38 mW 는 이 맥이 깨어 있을 때 쓰는 **6.6 W 의 0.57%** 이고, 78 Wh 배터리를 이것만으로
비우려면 2000 시간이 걸린다.

## 어떻게 쟀나

`powermetrics` 는 관리자 암호를 요구해 쓰지 못했다. 대신 세 가지를 조합했다.

**CPU** — `ps -o cputime` 의 60초 차이. `top` 의 `%CPU` 는 표본이 짧아 흔들리고,
`IDLEW` 는 구간값이 아니라 **누적값**이라 오해하기 쉽다(처음에 그렇게 잘못 읽었다).

**전력** — 배터리에서 직접 읽는다. 관리자 권한이 필요 없다.

```bash
ioreg -rn AppleSmartBattery   # "InstantAmperage"(2의 보수) × "Voltage" / 1000 = mW
```

`BatteryData` 블록 안에도 `"Voltage"=` 가 있어서 줄 앞을 고정해 뽑아야 한다.

**환산** — 시스템 전체 소비의 흔들림(±682 mW)이 앱보다 훨씬 커서 앱의 몫을 직접
빼낼 수 없다. 그래서 교정점을 하나 만들었다.

```
기준선 (창 닫힘)        6,579 mW
코어 1개 100% 부하     13,851 mW
                       ─────────
코어 100% 당            7,272 mW  →  0.517% ≈ 38 mW
```

> 이 교정은 **상한**이다. 부하를 만든 파이썬 루프가 코어만이 아니라 메모리·SoC 까지
> 함께 돌리므로 "코어 100% = 7.3 W" 는 과대평가다. 실제 앱의 몫은 38 mW 보다 작다.

## 무엇이 그 0.517% 를 쓰나

창이 열려 있으면 타이머 둘이 돈다.

| 무엇 | 주기 | 1회 비용 | 점유율 |
|---|---|---|---|
| `LocalhostManager.refresh()` | 2초 | **1.66 ms** | 0.083% |
| `CaffeinateScanner.refresh()` | 5초(접힘) / 2초(펼침) | **0.50 ms** | 0.010% |
| 합계 (스캔 자체) | | | **0.093%** |
| 측정된 전체 | | | **0.517%** |
| **차이 = 타이머·SwiftUI·렌더** | | | **0.42%** |

1회 비용은 753개 프로세스가 도는 상태에서 20회 평균으로 쟀다.

**여기가 핵심이다.** 스캔을 더 빠르게 만들어도 얻는 것이 적다 — 비용의 **4.5배가 스캔
바깥**에 있다. 타이머가 깨어나 `@Published` 를 건드리고 SwiftUI 가 다시 그리는 값이다.
줄이려면 **덜 자주 깨워야** 한다.

## 적용한 것 (2026-09-23)

아래 1·2번을 적용했다. 결과는 같은 방법으로 다시 쟀다.

| 상태 | 이전 | 이후 |
|---|---|---|
| 창 닫힘 | 0.000% | 0.000~0.050% |
| 창 열림 · **잠자기 방지 탭** | 0.517% | **0.083%** — 84% 감소 |
| 창 열림 · **로컬호스트 탭** | (0.517%) | **0.483%** |

로컬호스트 탭은 거의 그대로다. **그게 맞다** — 그 탭은 포트 목록을 보여주는 곳이라
스캔이 실제로 필요하다. 줄어든 것은 **나머지 세 탭**이고, 그것이 전부 낭비였다.

탭을 옮겨 다닐 때 두 목록이 제때 갱신되는 것과, 창을 열자마자 탭 아이콘 색이 맞게
나오는 것을 눈으로 확인했다 (2026-09-23).

1초 카운트다운 타이머 둘(`BlackWorkManager` · `LidWorkManager`)에는 tolerance 를
주지 않았다. 세션이 도는 동안에만 돌아 위 측정에 들어 있지 않고, `BlackWorkManager`
쪽은 화면 끄기 상태 기계가 그 주기에 기대고 있다(아래 *끈 상태로 유지* 참고).

3·4·5번은 적용하지 않았다. 1번을 적용하면 대개 한쪽 스캐너만 돌아 3번의 값이 크게
줄고, 4번은 측정상 0.17 ms 로 작다.

## 줄일 수 있는 것

값이 큰 순서다. **1·2번은 위에서 적용했다.**

### 1. 안 보이는 탭의 스캐너도 돈다 — 가장 크다 ✅ 적용

폴링을 켜고 끄는 자리가 `ContentView` 의 **루트**에 있다.

```swift
.onAppear { caffeine.startPolling() }
.onAppear { localhost.startPolling() }
```

그래서 잠자기 방지 탭을 보고 있어도 포트 스캔(1.66 ms)이 2초마다 돌고, 로컬호스트 탭을
보고 있어도 카페인 스캔이 돈다. **탭 4개 중 3개에서 포트 스캔은 전부 낭비**다.

보이는 탭의 스캐너만 돌리면 타이머 발생 횟수가 절반 가까이 줄고, 스캔 바깥 비용도
같은 비율로 줄어든다. 탭 전환 시 `onAppear`/`onDisappear` 로 붙이면 된다.

적용 결과 잠자기 방지 탭에서 **0.517% → 0.083%** 였다. 다만 탭 라벨의 점은 어느 탭에
있든 보이므로, 창이 열릴 때 **한 번은** 훑어야 처음부터 맞는 값이 나온다.

### 2. `Timer.tolerance` 를 주지 않았다 — 공짜에 가깝다 ✅ 적용

네 타이머 모두 오차 허용치가 0이다.

```swift
let timer = Timer(timeInterval: Self.interval, repeats: true) { … }
RunLoop.main.add(timer, forMode: .common)
```

macOS 는 오차를 허용한 타이머를 **모아서 한 번에 깨운다**. 2초 주기에 0.2~0.5초의
tolerance 를 주면 다른 타이머와 병합될 수 있다. 한 줄이면 되고 동작은 바뀌지 않는다.

```swift
timer.tolerance = Self.interval * 0.2
```

### 3. `ProcessSnapshot.all()` 을 사이클마다 두 번 부른다

카페인과 로컬호스트가 각자 부른다. 한 번에 **476 KB**(753 × 648 바이트)를 할당하므로
2초마다 약 1 MB 를 만들었다 버린다.

1번을 적용하면 대개 한쪽만 돌아 자연히 해결되지만, 둘 다 돌아야 하는 경우를 위해서는
스냅숏을 짧은 시간 공유하는 편이 낫다.

### 4. 경로·이름을 pid 별로 캐시하지 않는다

서명 정보는 캐시한다(`signingCache`). 그런데 `executablePath` 와 `friendlyName` 은
스캔마다 다시 부른다.

```
executablePath   0.01 ms (듣는 것 23개 전체)
friendlyName     0.16 ms (같은 기준)
```

작다. 다만 서명 캐시가 이미 있는 자리에 얹는 것이라 비용이 거의 없다.

### 5. 변화가 없어도 같은 주기로 깨운다

포트 목록은 몇 분씩 그대로인 것이 보통이다. 바뀌지 않으면 주기를 늘리고, 바뀌면
되돌리는 식으로 하면 조용한 시간대의 깨우기를 크게 줄인다. 대신 반응이 느려지므로
상한(예: 10초)을 둬야 한다.

## 줄이지 않는 것

**창 닫힘 상태** — 이미 0.000% 다. 여기서 더 얻을 것이 없다.

**`caffeinate` 자식 프로세스** — 앱이 띄우지만 CPU 를 쓰지 않는다. 커널에 assertion 을
걸어두고 잠들어 있을 뿐이다.

**API 소켓 서버** — `DispatchSource` 로 연결을 기다린다. 요청이 없으면 깨지 않는다.

**메뉴바 아이콘** — 타이머 없이 `objectWillChange` 를 구독한다. 상태가 바뀔 때만 다시 그린다.

## 이 앱의 진짜 전력 이야기

앱 자신이 쓰는 38 mW 는 이 앱이 **하는 일**에 비하면 반올림 오차다.

이 맥은 깨어 있는 동안 **6.6 W** 를 쓴다(실측). 잠자기 방지나 덮개 기능을 켜는 것은
그 6.6 W 를 계속 쓰게 만드는 일이다. 한 시간 켜두면 **약 6.6 Wh**, 78 Wh 배터리의
**8% 남짓**이다. 앱의 폴링을 완전히 없애도 이 값은 1%도 안 줄어든다.

> 잠든 맥의 소비는 재지 않았다. 재려면 화면을 꺼야 해서 이번 측정에서는 뺐다.

그래서 전력을 아끼려면 순서가 이렇다.

1. **다 쓰면 끈다.** 이 앱의 모든 절전 효과는 여기서 나온다
2. **창을 닫아둔다.** 폴링이 멈춘다. 기능은 메뉴바에서 계속 쓸 수 있다
3. 위의 1~5번 — 다 합쳐도 38 mW 안쪽의 이야기다

## 측정의 한계

- **기계 한 대**에서만 쟀다. M3 Pro / macOS 26.3.1 / 배터리 전원
- **`powermetrics` 를 못 썼다.** 프로세스별 에너지 영향, 패키지 전력, 웨이크업 상세를
  보려면 관리자 권한이 필요하다
- 코어당 전력 교정은 **상한**이다. 위 설명 참고
- 창 열림 측정은 **로컬호스트 탭이 아닌 상태**에서 했다. 목록이 화면에 그려지는
  탭에서는 렌더 비용이 더 붙는다 — 재지 않았다
